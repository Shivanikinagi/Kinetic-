# Arkiv friction log

Things that slowed us down while building KINETIC on `@arkiv-network/sdk`, with what we expected and what happened. Items 1 to 13 were found on SDK 0.8.1 and Tiramisu; from item 14 on, on SDK 1.0.1 and Rabdi, where KINETIC runs now.

1. **Upper-case attribute names pass the SDK but fail on-chain.** *Found on our first live write.* An offer with an attribute named `payTo` passed `isValidAttributeName` in the SDK, whose regex is `^[A-Za-z][A-Za-z0-9._-]*$`. It then reverted on Tiramisu with `Ident32InvalidByte(3, 0x54)`: the chain rejected the `T`. The SDK error text even lists `"A"-"Z"` as allowed. *Reproduce:* `createEntity({ attributes: { payTo: "x" }, … })` against `rpc.tiramisu.db-chain.testnet.arkiv.network`. *Expected:* the SDK to reject it client-side with the same rule as the chain, and the docs to state the charset. *Workaround:* every KINETIC attribute is snake_case (`pay_to`, `job_id`, `audit_ref`). *Re-checked against the docs on 2026-11-06:* the naming rules on [Define a schema](https://docs.arkiv.network/schemas/define/) now allow upper case and say names are case-sensitive. We haven't re-tested an upper-case name on Rabdi.

2. **Docs URLs redirect in chains.** `arkiv.dev.golem.network/docs/sdk` returns 308 to `docs.arkiv.network/typescript-sdk/querying-data`, which returns 301 to a trailing-slash `http://` URL. Tools that don't follow cross-host redirects, such as some fetchers and AI assistants, stop there. *Expected:* one stable HTTPS URL. *Re-checked on 2026-11-06:* the old URL now lands on a working page.

3. **Python SDK versions don't line up.** PyPI lists `arkiv-sdk` 1.0.0b2, while the docs reference SDK 0.6.0 and the skills guide targets 0.8.1 for TypeScript. We used the TypeScript SDK, because the prize rules name `@arkiv-network/sdk` or JSON-RPC. *Expected:* a version matrix per language.

4. **No "match everything" query.** `select().limit(3).fetch()` throws `InvalidPredicateError: A query needs at least one filter`. That's reasonable, but it makes "show me any entity on this chain" probes awkward when checking connectivity. *Workaround:* we always filter on our own `app` attribute.

5. **The docs disagree on which operators Rabdi supports.** [Filter results](https://docs.arkiv.network/querying/filter/) lists `ne` and `not`, but [Older networks](https://docs.arkiv.network/networks/older-networks/) says "Rabdi has no NOT or !=", and the [query language](https://docs.arkiv.network/reference/query-language/) reserves `NOT` as a keyword without listing it as a condition. On SDK 0.8.1 the JSON-RPC reference also said `!=`, `EXISTS` and `TYPEOF` were rejected; the query language page now lists `EXISTS` and `TYPEOF`. *Expected:* one table of the operators Rabdi accepts, and the SDK to reject the rest before sending. *Workaround:* KINETIC uses only `=`, comparisons, `AND` and `OR`.

6. **Bare numbers as attribute values are ambiguous.** It wasn't obvious which type a bare `number` maps to on write versus in an `eq()` filter. We tag every value explicitly with `str()` / `u64()` so writes and queries always match.

7. **One wallet means one nonce.** Concurrent `createEntity` / `patchEntity` calls from the same wallet would race on nonces. We built a write queue that merges patches and sends `executeBatch`. *Request:* a built-in batching or queued wallet client.

8. **`executeBatch` result ordering.** We rely on `createdEntities[i]` matching `creates[i]`. That seems to hold, but we couldn't find it documented. *Re-checked on 2026-11-06:* [Batches](https://docs.arkiv.network/writing/batches/) now says `createdEntities` lists the keys in the order of `creates`.

9. **Expiry is in blocks, UIs think in seconds.** `ExpirationTime.fromSeconds` is great for writing, but reads return `expiresAt` as a block number. A countdown in the dashboard needs block timing. *Request:* `expiresAtTimestamp` in query results.

10. **No programmatic faucet.** Our setup script creates and funds seven role wallets (verifier, buyer, five providers) from one faucet-funded wallet. A CLI or API faucet would make CI and multi-agent demos easier.

11. **Rate limits look like hangs.** *Found during a live run.* With five providers renewing offers and a dashboard polling five kinds every 2.5 s, the public Tiramisu RPC began answering every call with HTTP 429-style plain JSON, `{"error":"ANON_RATE_LIMITED","message":"unauthenticated rate limit exceeded; get an API key at https://hub.arkiv.network …"}`. That body isn't a JSON-RPC response, so viem's HTTP transport retried with backoff, and `select().fetch()` appeared to hang for over a minute with no error. *Reproduce:* `curl -X POST https://rpc.tiramisu.db-chain.testnet.arkiv.network -d '{"jsonrpc":"2.0","id":1,"method":"arkiv_getEntityCount","params":[]}'` in a loop until it flips. *Expected:* the limits in the docs, a JSON-RPC error with a code the SDK maps to a typed `RateLimitedError`, and an `apiKey` option on the SDK client. *Workaround:* bounded `timeout`/`retryCount` on the transport, the key sent as `X-API-KEY` via `fetchOptions.headers` (`ARKIV_API_KEY`), and one cached server-side read per kind for all dashboard viewers.

12. **No documented header for access keys.** We found `X-API-KEY` in a third-party skills guide, not in the SDK docs or README. *Expected:* the header name and an example next to `createPublicClient`. *Re-checked on 2026-11-06:* [Access keys](https://docs.arkiv.network/start-here/access-keys/) now documents all three forms: in the URL path, `X-API-KEY`, and a Bearer token.

13. **128-byte cap on string attributes, found at write time.** An HCS-14 UAID with its routing parameters is 176 bytes, and the offer write failed with `InvalidValueError … exceeds the 128-byte limit on a str. Store the long form in the entity payload and keep a short, queryable key`. The error is excellent (it names the fix). The cap is on the [Limits](https://docs.arkiv.network/reference/limits/) page, but the create and schema pages we read don't mention it, so we found it only on the first live write. *Workaround:* the attribute holds `uaid:aid:<hash>`, the payload holds the full UAID, and the emulator our tests run on now enforces the same cap.

14. **Moving to SDK 1.0 meant moving networks.** `@arkiv-network/sdk` 1.0 no longer speaks Tiramisu's protocol, so upgrading the SDK also moved KINETIC from Tiramisu (chain 7738577) to Rabdi (chain 7794095). Access keys are per network, so every role needed a new Rabdi key, and everything written on Tiramisu stayed behind there. Our older evidence links still point at the Tiramisu explorer, and `src/config.ts` keeps both networks so those chain ids and links still resolve. *Expected:* the [Older networks](https://docs.arkiv.network/networks/older-networks/) page now has a "Moving an old app forward" list, which we found after moving. We'd like that list linked from the SDK's release notes, and one key that works across Arkiv's testnets.

15. **Named schemas change every read.** With SDK 1.0 each kind is written through `defineSchema` (`kinetic.offer`, …) with typed columns, and the old `kind` attribute goes away. Entities written before the switch don't expire at once, so for a while every read has to match both shapes, `(arkiv.schema = … AND …) OR (kind = … AND …)` (`kindOfAttrs` in `src/integrations/arkiv.ts`). The verifier re-creates an old `reputation` entity on the new schema the first time it updates it. *Expected:* a documented way to migrate live entities to a schema, or a query helper that matches both.

16. **Writes ran out of gas during an RPC outage.**
    - **When:** on 2026-11-06 between 04:07 and 04:10 UTC. All five providers' offer heartbeats failed on Rabdi, for example [`0xd8513608…2b4d`](https://rabdi.explorer.arkiv.network/tx/0xd8513608487f809a32dc6e4afc914f1990f295422e48ead23cbe753704ec2b4d). Each heartbeat is one `extend` of the provider's offer.
    - **What happened:** the SDK threw `ran out of gas: it used all 31901 gas it was given, so nothing was applied and the fee was spent … Send it again`.
    - **Around it:** in the same minutes, `arkiv_query` calls to `rpc.rabdi.db-chain.testnet.arkiv.network` failed with `HTTP request failed`. By 04:21 UTC the RPC answered again.
    - **Expected:** the SDK explains the failure well, but it doesn't act on it. We expected the SDK to estimate with headroom, or to resend with more gas itself. Arkiv has a [status page](https://status.arkiv.network/); we didn't know about it at the time, and the SDK's errors could point to it.
    - **Workaround:** the heartbeat sends again on its next tick. An offer that lapses in the meantime is republished.
    - **Reproduce:** we couldn't on demand. Only the provider writes to its own offer, so we don't know what changed between the estimate and inclusion. It only happened while the RPC was failing.
